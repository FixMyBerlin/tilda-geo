# Migration: Bun → Node.js + nub

This repository was migrated from the **Bun** runtime/toolchain to **stock Node.js (LTS) driven by [nub](https://nubjs.com)**. nub is a Rust CLI that augments an existing Node install: it runs TypeScript directly, manages dependencies (pnpm‑compatible), and provisions Node versions — without being a separate runtime. The goal was a **direct replacement** of every Bun touch‑point, keeping behavior identical, not a broader rewrite.

> TL;DR: `bun` → `nub`, `bunx` → `nubx`, `bun.lock` → `lock.yaml`, the `bun` runtime APIs (`$`, `sql`, `Bun.*`) → small Node‑backed compatibility modules, and the production server now builds for Node (`nitro preset: 'node-server'`) instead of Bun.

---

## Why these replacements (decisions & rationale)

### Runtime & TypeScript execution — **nub**

Every `bun <file>.ts` became `nub <file>.ts`; shebangs `#!/usr/bin/env bun` → `#!/usr/bin/env nub`. nub transpiles TypeScript on stock Node and honors our `tsconfig` path aliases (`@/…`, `@/scripts/…`) at runtime, so script imports were unchanged. Node is pinned by **`.nvmrc` (`26`)**, which nub provisions automatically (Node 26.3.1) — including for `nub run` script bins like `tsc`/`vitest`.

**Which Node version.** Three signals bound the choice:

- _Framework floor:_ TanStack Start declares `engines.node: ">=22.12.0"` (Vite/Nitro: `^20.19.0 || >=22.12.0`).
- _Real app floor:_ Node 22 **does not work** — the test suite fails with `ReferenceError: Float16Array is not defined`, a global that only exists in **Node 24+** (used by the map/graphics dependency graph). So the effective minimum is Node 24.
- _Goal — run the newest that works, not the minimum._ The current release lines are: **24** = active LTS, **25** = odd/"Current" (near end-of-life, skip), **26** = latest (released April 2026, becomes LTS Oct 2026).

We pin the **latest that fully passes our checks: Node 26.3.1** — `.nvmrc` = `26`, and the Docker images use `node:26` / NodeSource `setup_26.x`. Verified on Node 26: both type-checks, lint, format, and **all 169 tests** pass. `engines.node` stays at **`>=24.0.0`** — that's the honest hard floor (`Float16Array`), so the package still declares compatibility with Node 24 LTS while we develop/CI/deploy on the newest 26. (Node 25 is intentionally skipped: it's odd-numbered and reaches end-of-life around now.)

> Note: on Node 26 there is a benign `DEP0205` warning (`module.register()` deprecated) emitted by the TS loader-hook registration (nub/vitest); it does not affect the run and will go away as those tools adopt `module.registerHooks()`. If you prefer to stay on active LTS, set `.nvmrc` to `24` — both are tested and supported.

### Package manager & lockfile — **nub‑owned `lock.yaml`**

`nub pm use nub` made nub the owning package manager. Per the brief ("use a lockfile that is native to nub, we don't have to stay with bun.lock") the native **`lock.yaml`** (pnpm‑v9 format) replaces `bun.lock`. The command also wrote `packageManager`/`devEngines.packageManager` to `package.json` and preserved the flat layout via `.npmrc` (`node-linker=hoisted`), so `node_modules` resolution matches what Bun produced.

### Parallel/sequential scripts — **npm-run-all2 (`run-p` / `run-s`)**

Bun's `bun run --parallel <glob>` / `--sequential <list>` have **no nub equivalent**. Even though nub advertises pnpm compatibility, it does **not** implement [pnpm's "Running multiple scripts"](https://pnpm.io/cli/run#running-multiple-scripts) feature — none of the forms a pnpm user would expect work (verified against nub 0.1.9):

| Attempt                                  | Result                                                                                     |
| ---------------------------------------- | ------------------------------------------------------------------------------------------ |
| `nub run "/^lint:/"` (pnpm regex form)   | `Error: missing script: "/^lint:/"`                                                        |
| `nub run --parallel "/^lint:/"`          | `Error: not in a workspace` — nub's `--parallel`/`--sequential` are _workspace_-level only |
| `nub run lint:a lint:b` (multiple names) | runs only `lint:a`; `lint:b` is passed to it as an **argument**                            |
| `nub run "lint:*"` (bun glob)            | `Error: missing script`                                                                    |

So a dedicated runner is required. We use **`npm-run-all2`** — `run-p` (parallel) / `run-s` (sequential) — which supports both globs (`dev:*`) and explicit lists. This is also the replacement endorsed by the [e18e module-replacements project](https://github.com/e18e/module-replacements/blob/main/docs/modules/npm-run-all.md) for the unmaintained `npm-run-all`: the **actively-maintained fork with identical syntax**. (e18e's alternatives — `concurrently` for parallel-only, Wireit for caching/dependency-graph builds — aren't needed here.) The mapping is mechanical:

- `bun run --parallel dev:*` → `run-p "dev:*"`
- `bun run --sequential a b c` → `run-s a b c`

### Loading repo‑root `.env` files — **`nub --env-file` + `dotenv-cli`**

Env files live one level above each package (`../.env`, `../.env.local`). nub's `--env-file` works for **file runs**, so `bun --env-file=../.env x.ts` → `nub --env-file=../.env --env-file-if-exists=../.env.local x.ts` (the `if-exists` variant keeps the optional local file from erroring). For **non‑file commands** (the `dev` orchestrator and the `prisma` CLI) nub can't combine `--env-file` with `exec`, so those use **`dotenv-cli`**: `dotenv -e ../.env -e ../.env.local -- <cmd>` (it silently skips a missing `.env.local`).

### The `$` shell — **tinyexec, wrapped in a Bun‑`$`‑compatible shim**

Our scripts use Bun's `$` heavily with its full chain API (`.text()`, `.quiet()`, `.nothrow()`, `.cwd()`, `.env()`) and rely on streaming output + throwing on non‑zero exit. The [e18e module-replacements project flags `execa`](https://github.com/e18e/module-replacements/blob/main/docs/modules/execa.md) and recommends the lighter **`tinyexec`** (a zero-dependency wrapper over `node:child_process`; `nanoexec` is the even-thinner alternative). We follow that recommendation and use **`tinyexec`**.

tinyexec takes an explicit `x(command, args, options)` — it has no `$` template tag. Rather than hand-split ~30 commands into `x()` calls across ~25 files (30 chances for an arg-ordering bug), we keep one small **Bun-`$`-compatible shim** (`scripts/lib/sh.ts` / `processing/utils/sh.ts`, ~150 lines incl. a template tokenizer) that backs `$` with tinyexec. Result: **call sites are unchanged except the import path**, the heavy `execa` dependency is gone, and the only bespoke logic — turning `` $`cmd ${arg}` `` into `[command, ...args]` — is centralized in one unit-smoke-tested place. The shim matches Bun's semantics: literal whitespace splits args; each interpolation is one escaped argument (so values with spaces are safe and `--file=${p}` / `${dir}:/mnt` stay single args); arrays expand to multiple args; default streams to the terminal while `.quiet()`/`.text()` capture; non-zero throws unless `.nothrow()`. There is no embedded shell, so the one command that used a pipe (`find … | sort | xargs shasum` in `processing/utils/hashing.ts`) was rewritten in plain Node.

> If a future need arises to drop even the shim, every `$` call site could be rewritten to tinyexec's `x()` directly — the tradeoff is losing the ergonomic template form and spreading arg-splitting across all files.

### The PostgreSQL client — split per package: `pg` in the app, postgres.js in processing

Bun's built-in `sql` is a re-implementation of **postgres.js** — tagged-template queries, the `sql(object)` helper for dynamic `INSERT`/`UPDATE`, `sql.unsafe(...)`, `.values()`, array-shaped results. We weighed `pg` (node-postgres) vs `postgres.js` against three axes — fewest dependencies, change complexity, and Prisma's direction — and the best answer differs per package:

**App → `pg`.** The app already depends on `pg` (directly, via Prisma's `@prisma/adapter-pg`, and in `scripts/topic-docs-coverage-check`, which already uses `pg`'s `client.query()`). **Prisma 7 removed its Rust query engine and now runs on a JS driver adapter; for PostgreSQL that adapter is `@prisma/adapter-pg`, built on `pg` — there is no postgres.js adapter** ([Prisma DB drivers](https://www.prisma.io/docs/orm/overview/databases/database-drivers), [upgrade to v7](https://www.prisma.io/docs/orm/v6/more/upgrades/to-v7)). So the app's DB layer is committed to `pg`, and that is Prisma's direction. The only app file using Bun's `sql` was `TranslationAnalysis/analyze.ts` (two simple `SELECT`s); rewriting it to `pool.query(...)` was trivial, **removed `postgres` from the app entirely**, and ended the intra-app inconsistency of two raw-SQL styles in one package.

**Processing → postgres.js.** Processing is a standalone pipeline that **does not use Prisma at all**, so Prisma's direction does not apply here. Its Bun `sql` usage is the heavy part — dynamic `sql(object)` `INSERT`/`UPDATE`, `sql.unsafe`, `.values()` across ~6 files — and `postgres.js` is a **zero-dependency** drop-in (only the import path changes). Switching processing to `pg` would _add_ pg's transitive dependency tree to this otherwise lean package **and** require a bespoke parameterized INSERT/UPDATE builder — more code and risk for _more_ packages, not fewer. So processing keeps `postgres.js` (shared client in `processing/utils/sql.ts`, mirroring Bun's connection discovery: `DATABASE_URL`/`POSTGRES_URL`, then libpq `PG*`).

Net dependency effect: `postgres` is gone from the app (pg was already present), and processing carries the single zero-dep `postgres` package. Because postgres.js keeps a pool open, `processing/index.ts` calls `sql.end()` and the app's `analyze.ts` calls `pool.end()` on completion — so processes exit cleanly, as they did under Bun. The app server's Prisma + `pg` stack is untouched.

### Other `Bun.*` runtime APIs — **thin Node shims**

`Bun.write`, `Bun.file`, `Bun.spawn`, `Bun.spawnSync`, `Bun.argv`, and `Bun.YAML` map to a small compat module **`app/scripts/lib/bun.ts`** backed by `node:fs`, `node:child_process`, `process.argv`, and the **`yaml`** package. Migration was then mechanical: add a named import and drop the `Bun.` prefix (`Bun.write(…)` → `write(…)`). The shims match Bun's defaults (e.g. `write` auto‑creates parent dirs; `spawn` exposes `{ stdout, stderr, exited, exitCode }` as web streams so `new Response(proc.stdout).text()` keeps working; stdio defaults `ignore`/`pipe`/`inherit`). **Processing** only used `Bun.file`/`Bun.write` (no `spawn`/`argv`/`YAML`), so rather than duplicate this module it inlines those few calls to `node:fs` directly — see _Shared code & duplication_ below.

### Bun‑only `import.meta` / CJS globals

nub provides Node's `import.meta.dirname` / `import.meta.filename` / `import.meta.main`, but **not** Bun's `import.meta.dir` / `import.meta.file`, nor CommonJS `__dirname` / `__filename` / `require.main` in ESM. These were rewritten repo‑wide (`import.meta.dir` → `import.meta.dirname`, `require.main === module` → `import.meta.main`, etc.).

### Production server runtime — **Nitro `preset: 'node-server'`**

This is the most behavioral change. The app server was built with `nitro({ preset: 'bun' })`, i.e. the production bundle (`.output/server/index.mjs`) targeted the Bun runtime. It is now **`preset: 'node-server'`** and is launched with `node .output/server/index.mjs`.

## How this affects the app

- **Local dev / CI / prod all run on Node 24 + nub** instead of Bun. `nub install`, `nub run <script>`, `nubx <bin>` replace their `bun*` equivalents.
- **The production container changed base images.** `app.Dockerfile`: `oven/bun:1` → `node:26-trixie-slim` + global `@nubjs/nub`; it builds the Node‑server output and runs `nubx prisma migrate deploy && node .output/server/index.mjs`. `processing.Dockerfile`: the `curl … bun.sh/install` step → Node (via NodeSource) + `@nubjs/nub`; entrypoint `bun run /processing/index.ts` → `nub /processing/index.ts`.
- **Peer dependencies must now be explicit.** Bun auto‑installs peers; nub (pnpm‑style) does not. `@testing-library/dom` (a peer of `@testing-library/react`) was added explicitly to fix type‑checking and tests. Watch for other previously‑implicit peers.
- **The install‑time "cooldown" moved.** `bunfig.toml`'s `minimumReleaseAge` (5‑day hold on fresh packages) has **no nub/pnpm‑native equivalent yet**, so it was removed. The equivalent protection now lives entirely in Dependabot's native `cooldown` (`.github/dependabot.yml`), and the lockfile‑sync workflow no longer passes `--minimum-release-age`.
- **`packageManager: "nub@…"` is non‑standard for Corepack.** Contributors must have nub installed (`npm install -g --ignore-scripts=false @nubjs/nub`); a Corepack‑enabled shell will otherwise error. Hosted bots (Dependabot/Renovate) cannot regenerate `lock.yaml`, so the **`Sync Dependabot lock.yaml`** workflow regenerates it with `nub install` after Dependabot bumps `package.json`.
- **Verification:** `nub run type-check` (app + processing), `nub run check-format`, `nub run check-lint` (zero warnings), and `nub run test-run` (**169 tests, 37 files — all passing**) succeed. The compat layer (`$`, `write`/`file`, `YAML`, `spawnSync`) was also smoke‑tested at runtime. Docker image builds were **not** run in this environment and should be validated in CI/deploy.

## New developer setup

```bash
npm install -g --ignore-scripts=false @nubjs/nub   # one-time: install the nub CLI
cd app && nub install                              # installs deps; nub provisions Node 26 from .nvmrc
nub run dev                                         # or any package.json script
```

The Bun‑compat helpers live in `app/scripts/lib/` (`sh.ts`, `bun.ts`) and `processing/utils/` (`sh.ts`, `sql.ts`). For an **app** script that needs another Bun API, add it to `app/scripts/lib/bun.ts`; in **processing**, use `node:fs` / `node:child_process` directly (there is no Bun global on Node). See _Shared code & duplication_ for why `sh.ts` is the only file kept in both folders.

### Shared code & duplication

These are **two independent packages with independent Docker build contexts** — `processing.Dockerfile` does `COPY processing /processing/`, so anything under `app/` is simply absent from the processing image. A static `import` of a shim in `app/` would therefore break the processing container. (The one shared _config_, `app/oxfmt.config.mjs`, works only because the code resolves it at runtime via a path-fallback chain — not something a static `import` can do.) Truly single-sourcing code across the two would require either a workspace package both Dockerfiles install, or publishing — both larger structural changes.

So we **minimized** duplication instead of forcing it:

- `bun.ts` (`file`/`write`/`argv`/`spawn`/`spawnSync`/`YAML`) lives **only in `app/`**. Processing used just `file`/`write`, so those ~15 call sites were inlined to `node:fs` and the processing copy was deleted.
- `sql.ts` (postgres.js) is **processing-only**; the app uses `pg`.
- `sh.ts` (the `$` shim) is the **one file kept in both**. Processing uses `$` in ~17 files with the full chain (`.text()`/`.quiet()`/`.nothrow()`) and stream-by-default; rewriting those ~30 call sites to bare `tinyexec.x()` would lose the ergonomics and add risk, so the ~150-line shim is duplicated deliberately. If that bothers you, the clean fix is a small shared workspace package — captured as a follow-up.

## Known gaps / follow‑ups

1. **No install‑time `minimumReleaseAge` in nub.** Re‑evaluate if nub adds a pnpm‑style `minimum-release-age` setting; until then Dependabot `cooldown` is the only gate.
2. **nub `run` doesn't implement [pnpm's "Running multiple scripts"](https://pnpm.io/cli/run#running-multiple-scripts).** Despite nub's pnpm‑compatibility claim, `nub run "/regex/"`, multiple script names, and globs are all unsupported, and `--parallel`/`--sequential` are workspace‑only (see the table above). We depend on `npm-run-all2` for this. If a future nub version adds the pnpm multi‑script syntax, the `run-p`/`run-s` calls in the package.json scripts could be folded back into `nub run` and the `npm-run-all2` dependency dropped.
3. **Node: pinned to the latest (26), floor is 24.** We run Node 26.3.1 (`.nvmrc`/Docker), the newest line that passes all checks. Node 24 is the hard floor (`engines.node >=24.0.0`) because Node 22 can't run the suite (`Float16Array is not defined`). Node 26 becomes LTS in Oct 2026; until then it's "Current" — if you'd rather track active LTS, set `.nvmrc` to `24` (also tested). A benign `DEP0205` (`module.register()`) warning appears on Node 26 from the TS loader hooks; harmless. When Node 28 ships, re-run the checks and bump.
4. **Docker images unbuilt here.** Build `app.Dockerfile` / `processing.Dockerfile` in CI to confirm Node base + NodeSource + `nub install` resolve as expected. Verify the `node:26-trixie-slim` tag and NodeSource `setup_26.x` exist for the registry in use (Node 26 is recent — fall back to `node:24-*` / `setup_24.x` if a base isn't available).
5. **Watch for other implicit peer deps** that Bun used to auto‑install but nub does not.
6. **`generate-deploy-env.ts`** (run in `setup-env.yml`) imports `app/src` modules; it relies on `app/node_modules` resolution exactly as it did under Bun — unchanged, but worth a CI smoke check.
7. **`sh.ts` (the `$` shim) is duplicated in `app/` and `processing/`.** This is deliberate — the two are independent packages with independent Docker contexts, so a static cross-folder `import` can't be shared (see _Shared code & duplication_). `bun.ts` and `sql.ts` are no longer duplicated. To fully single-source `sh.ts`, convert the repo to a workspace with a shared package both Dockerfiles install — a larger change left as a follow-up. If the two copies drift, that's the signal to do it.
